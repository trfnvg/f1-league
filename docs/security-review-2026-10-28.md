# Проверка безопасности Fastlap — 28 октября 2026

Проверены исходники, текущие маршруты, жизненный цикл аркадных попыток,
сохранение прогнозов, роли лиг, загрузка аватаров, настройки Django и зависимости.
На рабочем сайте выполнен только анонимный HEAD главной; на GitHub — чтение
публичных метаданных репозитория. Продакшен-база не открывалась и не изменялась.
Это прикладное ревью, не полный пентест и не подтверждение защищённости облака.

## Срочно: база в публичном репозитории

Git отслеживал `db.sqlite3` вопреки `.gitignore`. Read-only запрос подтвердил
три записи `auth_user`; имена, почта и хеши паролей в отчёт/логи не выводились.
Не установлено, являются ли эти записи действующими продакшен-аккаунтами.
Анонимный GitHub API показал `private=false` для `trfnvg/f1-league`.
В ходе работы владелец сообщил, что переключил репозиторий в Private и
подтвердил DEBUG=False, длинный существующий ключ и явный список хостов.
Это не отзывает возможные ранее скачанные копии.

База удалена из текущего Git-индекса, **локальный файл сохранён**. Docker и ранее
исключал SQLite и `.git`; это не доказывает отсутствие скачиваний из GitHub.
В старой истории база остаётся. Самостоятельно не переписывались история,
права репозитория, аккаунты, пароли и облачные настройки.

Нужны действия владельца:

1. Закрыть репозиторий: GitHub Settings → General → Danger Zone → Private.
2. Проверить, совпадают ли локальные аккаунты с реальными. Для совпадающих
   сменить пароли; при необходимости отозвать сессии. Не публиковать содержимое БД.
3. Согласовать отдельное удаление базы из Git-истории и обновление всех клонов.
   Приватность/очистка не отзывают уже скачанные копии и публичные форки.
4. Если в истории найдутся реальные API/SMTP/БД-ключи, перевыпустить именно их.
   Этот обзор не доказывает утечку таких ключей; их значения не запрашивались.

## Где на самом деле хранятся результаты

| Данные | Источник истины |
| --- | --- |
| Рекорды и число попыток игр | `ArcadeRecord` / `DoodleRecord`, серверная БД |
| Попытки, привязка к этапу и время завершения | `ArcadeAttempt` / `DoodleAttempt`, серверная БД |
| Зафиксированный рейтинг этапа, колесо, трофеи | Серверные модели/снимки |
| Рекорд гостя и настройка пропуска вступления | Браузер; не участвуют в серверном зачёте |

Проблема была не в месте хранения: Cowboy GP принимал присланный клиентом
счёт вплоть до 2 147 483 647 без проверки времени. У Flappy была только грубая
проверка длительности. Само наличие БД и CSRF не подтверждает честность счёта.

## Что исправлено

- Общий серверный протокол start → checkpoints → finish для двух игр.
  Случайный одноразовый токен, привязка к пользователю/сессии/игре; в БД только
  хеш токена. Токен из другой сессии не отменяет чужую попытку.
- Одна незавершённая рейтинговая попытка на аккаунт: старт другой игры/вкладки
  закрывает предыдущую без результата. Завершение одноразовое; блокировки
  пользователя сериализуют изменения между играми/воркерами.
- Проверки типов, диапазонов, кодировки и размера JSON (4 КБ), серверного времени,
  монотонности счёта, общего и промежуточного прироста. Неуспешная проверка
  времени/счёта закрывает попытку без рекорда; причина сохраняется в БД и журнале
  без токенов/почты/тела запроса. Статусы видны в Django Admin для обеих игр.
- Серверные отметки прогресса каждые 10 секунд, максимум 12 часов на попытку,
  3 минуты без отметок. Это также означает: долгая потеря сети/приостановка
  браузера может сделать забег нерейтинговым. Игра продолжается, ошибка сохранения
  показывается; графика/разрешение/физика не урезались.
- Отдельные DB-лимиты игровых запросов: 120 start/update запросов на пользователя
  в минуту в каждой группе, 6000 на IP. Прокси-IP нельзя слепо брать из заголовка:
  применяется существующая настройка `AUTH_TRUSTED_PROXIES`.
- Старые дублирующие обработчики start/finish перенаправлены на общий протокол.
  Запросы без токена не сохраняют результат. Прототип «Сапёра» больше не принимает
  игровые результаты обычных пользователей даже при старой публичной настройке.
  После выкладки уже открытые старые игровые вкладки нужно обновить; начатая
  по старому протоколу попытка не будет задним числом считаться проверенной.
- Тесты staff не создают публичных попыток. Локальный рекорд залогиненного
  пользователя больше не является источником показателя рекорда; нужен ответ БД.
  Копия гостя не импортируется в общий рейтинг. Finish ждёт незавершённый checkpoint.
- No-store для персонализированных игровых ответов, сохранены CSRF, POST-only
  и серверная проверка владельца. Проверены дедлайн и неизменность зафиксированного зачёта.
- Ограничены регистрации (20/15 мин на IP) и проверки текущего пароля в настройках
  (10/15 мин на аккаунт, 60/15 мин на IP). Лимиты входа/восстановления сохранены.
- Аватары: до 5 МБ / 4096 px, декодирование и безопасная перекодировка в WebP
  без EXIF/дописанного содержимого, максимум 1024 px, сохранение пропорций и альфы.
  Старые файлы и игровые изображения не переписываются.
- Django 6.0.2 → 6.0.9; Pillow → 13.0.0, sqlparse → 0.6.0, urllib3 → 2.8.0.
  Исправления Django выпущены [6 октября](https://www.djangoproject.com/weblog/2026/oct/06/security-releases/).
  После обновления `pip-audit -r requirements.txt` с разрешением зависимостей
  не нашёл известных уязвимостей. Это не гарантия отсутствия неизвестных проблем.

## Ограничение античита — ещё открытая задача

**Сейчас реализована проверка правдоподобия, а не доказательство прохождения.**
Модифицированный JavaScript всё ещё может имитировать допустимый рост очков,
менять коллизии или автоматизировать управление. Токен/heartbeat не делают
клиент доверенным. Секрет в JavaScript, подпись клиентского числа или запрет
DevTools эту проблему не решают. Проверка на сервере необходима независимо
от живых подсказок, как поясняет [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html).

Для полноценной проверки соревнований нужен отдельный этап: фиксированный
такт симуляции и seed уровня от сервера, ограниченный журнал ввода, повторное
прохождение на сервере с проверкой коллизий и вычислением очков. Либо полностью
серверная симуляция. Начать проще с Flappy. Это изменение игровой архитектуры,
его нельзя выдавать за готовое в текущем патче. Боты, честно проходящие симуляцию,
тоже требуют отдельной политики/аналитики.

Существующие рекорды, трофеи и снимки не удалены и не объявлены задним числом
проверенными. Историческую накрутку без телеметрии достоверно установить нельзя.

## Перед выкладкой: конфигурация и облако

`python manage.py security_audit` выводит только флаги, не секреты. С `--strict`
команда запрещает production-запуск с DEBUG, слабым/дефолтным SECRET_KEY,
wildcard Host, небезопасными cookies, без CSRF или без явного DATABASE_URL.
`start.sh` запускает её **до**
миграций. Поэтому настройки нужно проверить перед деплоем, а не после сбоя.
Дефолтный `SECRET_KEY` оставлен только для локальной работы; production через
`start.sh` с ним не запускается. Прямой запуск Gunicorn в обход скрипта не защищён
этим стартовым барьером — использовать `start.sh`.

- `DEBUG=False`; существующий случайный `SECRET_KEY` ≥50 символов. Не менять
  хороший ключ без причины: он связан с сессиями, восстановлением и приглашениями.
- `ALLOWED_HOSTS=fastlap.ru,www.fastlap.ru,<реальный-хост-Timeweb>`, без `*`.
  Без env дефолт теперь ограничен Fastlap и localhost. Не угадывать хост health-check.
- Нужен production `DATABASE_URL`, иначе после изъятия SQLite из репозитория
  деплой без внешней БД может создать пустую локальную базу. Ничего не переносилось
  автоматически; резервная копия БД — перед миграцией 0057.
- Secure/HttpOnly/SameSite session cookies; начальный HSTS 300 секунд, без
  includeSubDomains/preload. HEAD рабочего HTTPS-сайта до изменений подтвердил
  nosniff, DENY и same-origin Referrer-Policy; HSTS ещё отсутствовал.
- Выполнить на сервере `python manage.py check --deploy` и `security_audit --strict`.
  HTTPS redirect может выполнять прокси Timeweb, а не Django. Прокси должен удалять
  присланные извне X-Forwarded-* и задавать свои; CIDR для rate-limit брать у провайдера.
- Отдельно проверить: firewall PostgreSQL (только приложение), приватность S3,
  запрет исполнения загрузок, ingress-лимит размера файлов, TLS, резервные копии
  и восстановление, права service accounts, логи и мониторинг ошибок.
  Доступа к панели Timeweb/почте/сетевым правилам в этой задаче не было.

Основа проверки: [Django deployment checklist](https://docs.djangoproject.com/en/6.0/howto/deployment/checklist/).

## Проверки

- Django: отдельная in-memory БД, полный набор + сценарии подделки/чужих сессий/
  повтора/истечения/CSRF/лимитов/старого клиента/перекодировки аватара.
- Chromium и WebKit: реальные игровые JS/шаблоны на 390/1440 px с моками HTTP.
  Подменённый localStorage игнорируется, токен передаётся в checkpoints/finish,
  рекорд обновляется только после подтверждения. Серверные проверки тестируются
  отдельно; это не заявление о сквозном тесте на production.
- Регрессия таблиц аркад, мобильный WebKit для остальных страниц.
- `makemigrations --check`, проверка JS-синтаксиса, аудит зависимостей.
- Конкуренция проверена кодом блокировок и последовательными SQLite-тестами;
  отдельный нагрузочный/параллельный прогон PostgreSQL ещё нужен.
