# Этап 1: надёжность перед публичным запуском

## Границы

Код не меняет правила игр, качество графики, очки и схему БД. Он не включает
мониторинг в стороннем аккаунте и не создаёт production-бэкапы автоматически.
Ни секреты Timeweb, ни данные настоящих игроков для CI не нужны.

## Что работает после публикации

- `GET /health/live/` — процесс приложения отвечает, без обращения к БД.
- `GET /health/ready/` — дополнительно выполняет read-only `SELECT 1` в БД;
  недоступная БД даёт 503 без текста исключения. Проверка не подтверждает
  наличие всех миграций, исправность S3, SMTP или игрового начисления.
- Ответы проб не кэшируются. Они не отправляют почту и не создают записи.
- `X-Request-ID` — сгенерированный сервером идентификатор запроса.
- JSON-журнал содержит имя маршрута, метод, статус, длительность. Запросы
  дольше 1500 мс отмечаются WARNING, ответы 5xx — ERROR. Порог задаётся
  `SLOW_REQUEST_MS`. Успешные health-запросы не засоряют журнал приложения.
- Access-log Gunicorn больше не содержит IP, query string, cookie, User-Agent
  и URL с токеном приглашения/сброса. Для сопоставления есть request ID.
- Диагностика JS работает через свой домен: имя нашего JS-файла, строка,
  столбец, тип исключения и категория размера экрана. Не передаёт текст
  ошибки, форму, URL страницы, email, имя игрока или запись экрана.
  До 3 разных ошибок за загрузку страницы, без повторных отправок; endpoint
  защищён CSRF и общим для процессов лимитом 30 сообщений/5 мин на IP.
  Источник браузерного сообщения недоверенный: это сигнал, не доказательство.
  Отключение: `BROWSER_ERROR_REPORTING=False`.
- Стандартные серверные ошибки логируются без значений исключений, исходных
  сообщений, SQL и локальных переменных; остаются тип и позиции в стеке.

Логи инфраструктуры Timeweb и его прокси настраиваются отдельно: приложение
не может гарантировать, что провайдер не пишет URL в свои журналы.

## Подключить уведомления об ошибках

1. Создать проект Django в выбранном сервисе, совместимом с Sentry SDK
   (свой Sentry или облачный сервис). Проверить условия хранения данных.
2. В Timeweb добавить `SENTRY_DSN` из этого проекта, `APP_ENVIRONMENT=production`.
   DSN не публиковать в чате/репозитории. Секретные API-токены сервису не нужны.
3. `APP_RELEASE` — идентификатор опубликованного коммита; обновлять при релизе.
4. Настроить получателя уведомлений и правило о новых ERROR. Ошибки браузера
   отмечены событием `browser_runtime_error`; серверные 5xx — `http_request`.
5. Сначала на отдельном staging-окружении проверить тестовую ошибку и получение
   уведомления. Не создавать публичный URL, намеренно вызывающий 500.
6. В production проверить штатный вход/прогноз/аркаду и отсутствие новых ошибок.

После добавления DSN на staging можно отправить безопасное тестовое событие:

```sh
python manage.py shell -c "import logging, sentry_sdk; logging.getLogger('fastlap.operations').error('monitoring_test'); sentry_sdk.flush(timeout=5)"
```

Завершение команды не доказывает доставку: найти событие `monitoring_test`
в проекте и проверить, что уведомление действительно пришло получателю.

Без DSN сайт работает штатно, записи доступны в логах Timeweb, но внешние
уведомления об ошибках НЕ включены. Трассировки производительности и replay
пользовательских сессий выключены. Перед отправкой SDK удаляет запросы,
cookies, пользователей, breadcrumbs, значения исключений и локальные переменные.

## Внешняя проверка доступности

Добавить в выбранный uptime-сервис HTTPS-проверку
`https://fastlap.ru/health/ready/` раз в минуту: ожидается 200 и `status=ok`.
Уведомлять после 2–3 последовательных неудач и при восстановлении. Это
уведомит даже при полном падении приложения, когда оно не может отправить
ошибку само. Получателя и сервис нужно настроить отдельно.

В панели Timeweb путь проверки состояния — `/health/live/`, чтобы отказ БД
не вызывал цикл перезапусков. Проверка выполняется локально, поэтому точные
loopback-адреса сохраняются в ALLOWED_HOSTS даже при явном списке public-доменов.
`/health/ready/` проверяется внешним мониторингом: он дополнительно проверяет БД.
Источник: https://timeweb.cloud/docs/apps/healthcheck-path.

В `start.sh` откачен добавленный блокирующий `security_audit --strict`: новая
политика ключей мешала запуску ранее работавшего сайта. Проверка остаётся в CI
и доступна оператору вручную. Скрипт всё ещё требует DATABASE_URL и останавливается
при ошибке миграций/статики. В выводе ошибки теперь есть этап запуска и exit code.
Реальный запуск (миграции → статика → Gunicorn → HTTP) проверяется через
`python tests/startup_smoke.py` на отдельной временной БД, без данных Timeweb.

После релиза:

```sh
python scripts/check_release.py https://fastlap.ru
```

## Проверки перед деплоем

`.github/workflows/quality.yml` запускается на push/PR в main и вручную:

1. Python 3.12, изолированный PostgreSQL 16; без production-секретов.
2. Проверки Django/безопасности, отсутствия забытых миграций, синтаксиса JS.
3. Проверка известных уязвимостей production-зависимостей.
4. Миграции с нуля и `pg_dump`/`pg_restore` на искусственной БД.
5. Все backend-тесты, включая одновременные игровые запросы и rate-limit.
6. Сборка статики и smoke-проверки Chromium/WebKit, телефона и ПК.

**Важно:** GitHub Actions сам по себе НЕ блокирует независимый автодеплой
Timeweb! Пока интеграция не настроена, отключить автодеплой на push и запускать
публикацию вручную только для коммита с зелёным `Fastlap quality / checks`.
Включить Actions в приватном репозитории, проверить доступную квоту. Если
тариф GitHub поддерживает защиту ветки, сделать этот check обязательным для
слияния PR в main. Не считать защиту включённой только потому, что файл добавлен.

Не подключать workflow PR к production-окружению или его секретам.
Восстановление CI работает только для пустой локальной БД `fastlap_ci`,
создаёт **новую** `fastlap_restore_ci`, не удаляет и не перезаписывает БД.
Это проверка процедуры на тестовых данных, НЕ проверка копии рабочей базы.

## Реальные бэкапы: действия в Timeweb

1. Проверить, что для PostgreSQL включены автоматические копии; записать
   частоту, срок хранения, время последней успешной копии и контакт при сбое.
   Для начала ориентир: ежедневные копии и отдельная копия перед миграциями.
   При ежедневной копии без PITR потенциально теряется до суток изменений:
   перед гоночными дедлайнами выбрать более частое резервирование/PITR,
   если это поддерживается тарифом. Допустимую потерю данных согласовать явно.
2. Отдельно проверить копии S3/media: бэкап PostgreSQL не содержит аватары.
   Версионирование, если доступно, не заменяет независимую резервную копию.
3. Создать отдельную тестовую БД/кластер и восстановить туда выбранную копию.
   **Не нажимать восстановление поверх рабочей БД.** Убедиться по адресам,
   что staging не использует production-БД, бакет, SMTP или внешние уведомления.
4. Ограничить доступ к стенду. Восстановленная база содержит персональные
   данные; не переносить её в GitHub, CI, чат или публичные артефакты.
5. Проверить миграции, количество участников/прогнозов/очков, выборочно
   связи результатов, вход разрешённой тестовой учёткой и чтение изображений.
   Не запускать на копии массовые письма/выдачу наград.
6. Записать дату, выбранную копию, фактическую потерю данных по времени,
   продолжительность восстановления и результат. Повторять перед крупными
   изменениями и периодически (например, раз в месяц).

База, временные дампы и экспортированные журналы не должны попадать в Git
или Docker build context. Дампы хранить вне репозитория, шифровать и выдавать
доступ только владельцу. Возврат старого коммита НЕ откатывает миграцию:
перед несовместимыми изменениями нужен отдельный план и проверенная копия.

## Критерии завершения этапа

- [ ] Workflow зелёный на опубликованном SHA; CI действительно обязателен до релиза.
- [ ] Обе health-проверки проходят снаружи после публикации.
- [ ] Получено тестовое уведомление об ошибке на staging.
- [ ] Внешний uptime-монитор уведомляет о недоступности и восстановлении.
- [ ] Подтверждены production-бэкапы БД и media, выполнено отдельное восстановление.

До выполнения внешних пунктов внедрена кодовая часть этапа, а не весь
эксплуатационный процесс. Шаг 2 (проверка физики/повторов аркад) сюда не входит.

## Локальная проверка кодовой части — 28.10.2026

- 406 backend-тестов на отдельном PostgreSQL 16.15, без пропусков; миграции с нуля.
- Конкурентные запросы: один финальный результат, одна активная попытка,
  атомарный общий rate-limit. Соединения тестовых потоков явно закрываются.
- Реальный `pg_dump`/`pg_restore` в новую тестовую БД: история миграций,
  искусственная учётка и связанный профиль совпали. Production-копии не читались.
- Диагностика JS и обе аркады: Chromium/WebKit, 390 и 1440 px.
- WebKit: 38 настоящих страниц на двух размерах, включая формы и управление лигой.
- Статика собрана; синтаксис 33 JS-файлов проверен; забытых миграций нет.
- Аудит production-зависимостей не нашёл известных уязвимостей на момент проверки.
- Sentry проверен через локальный транспорт, без отправки данных во внешний сервис.

Сам workflow GitHub Actions ещё не запускался на GitHub; его успешный запуск,
деплой, доставка уведомлений и production-восстановление этим списком не подтверждаются.
